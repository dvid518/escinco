# F7.5_AUDITORIA_M4_M5.md — Auditoría de datos para migraciones M4 y M5

## 1. Estructura de datos esperada

### 1.1 Cuentas (colección `cuentas` en Firestore)

| Campo | Tipo | Descripción |
|-------|------|-------------|
| `id` | string | Identificador único |
| `tipo` | string | `banco`, `efectivo`, `plazo`, `debito`, `broker`, `exchange` |
| `moneda` | string | `PEN`, `USD`, `USDT`, `EUR` |
| `esPatrimonio` | boolean | `true`/`false` (toggle patrimonio) |
| `esAbstracta` | boolean | `true` para padres abstractos, `false` para cuentas reales |
| `padreId` | string \| null | ID del padre (para subcuentas) o `null` para cuenta raíz |
| `estado` | string | `activa`, `archivada` |
| `saldoInicial` | number | Saldo inicial de la cuenta |
| `moneda` | string | Divisa de la cuenta |
| `uid` | string | UID del usuario |
| `...` | otros campos | preferencias, timestamps, etc. |

### 1.2 Posiciones (colección `posiciones` en Firestore)

| Campo | Tipo | Descripción |
|-------|------|-------------|
| `id` | string | Identificador único |
| `activoId` | string | ID del activo (BTC, ETH, etc.) |
| `cantidad` | number | Cantidad del activo |
| `divisa` | string | Divisa del activo (`pen`, `usd`, `usdt`) |
| `custodioId` | string \| null | ID de la cuenta custodio (`null` = legacy, pendiente M5) |
| `tipo` | string | `posicion` |
| `ultimaActualizacion` | Date | Fecha de última actualización |

## 2. Tipos de elementos a identificar en M4–M5

### 2.1 Pestañas cripto legacy (M4)

Criterio: cuentas con `tipo === "exchange"` y `esPatrimonio === false`.

Características:
- No efectivo propio (es un contenedor)
- Su efectivo está en subcuentas (modelo E2) o no se cuenta
- `padreId` apunta típicamente al exchange padre
- `padreId === "exchange"` indica exchange directo

### 2.2 Posiciones legacy (M5)

Criterio: posiciones con `custodioId === null`.

Características:
- No contabilizan en F7.3 hasta M5
- Pueden tener `activoId` definido
- Pueden ser `únicas` o `ambiguas` (mismo activo en varios custodios posibles)

### 2.3 Casos adicionales

| Caso | Descripción | Acción M4 | Acción M5 |
|------|-------------|-----------|-----------|
| **Pestaña sin posición** | Cuenta exchange sin posiciones asociadas | Mantener legacy | Mantener pendiente_asignacion |
| **Posición sin pestaña** | Posición con custodioId null sin cuenta exchange correspondiente | Mantener legacy | Asignar custodio si es posible |
| **Múltiples custodios** | Misma posición, varios broker/exchange posibles | Marcar pendiente_asignacion | Requerir decisión usuario |
| **Pestaña + posición única** | Un exchange + una posición del mismo activo | Fusionar (mover posición a custodio del exchange) | Asignar custodioId del exchange |
| **Pestaña + múltiples posiciones** | Mismo exchange, varias posiciones del mismo/u distinto activo | Proporcionar opciones al usuario | Proporcionar opciones al usuario |

## 3. Datos de prueba identificados (basados en modelo)

### 3.1 Pestañas cripto legacy (buscar en datos reales)

Buscar cuentas donde:
- `tipo === "exchange"`
- `esPatrimonio === false`
- `padreId === "exchange"` (exchange directo)

**Ejemplo hipotético de datos:**
- Cuenta `cExchange`: `tipo: "exchange"`, `esPatrimonio: false`, `padreId: "exchange"`, `moneda: "BTC"`, `esAbstracta: false`
- Cuenta `cExchange2`: `tipo: "exchange"`, `esPatrimonio: false`, `padreId: "exchange"`, `moneda: "ETH"`, `esAbstracta: false`

### 3.2 Posiciones legacy (buscar en datos reales)

Buscar posiciones donde:
- `custodioId === null`

**Ejemplo hipotético de datos:**
- Posición `pBTC1`: `custodioId: null`, `activoId: "BTC"`, `cantidad: 0.5`
- Posición `pETH1`: `custodioId: null`, `activoId: "ETH"`, `cantidad: 2`

### 3.3 Posiciones con custodio inválido

Buscar donde:
- `custodioId` definido pero la cuenta no existe o no es `broker`/`exchange`

**Ejemplo:**
- Posición con `custodioId: "cuenta_fantasma"` que no existe en la colección de cuentas

### 3.3 Pestañas sin posición correspondiente

- Cuenta exchange `esPatrimonio: false` sin posiciones `custodioId` que la referencien

### 3.4 Posiciones sin pestaña correspondiente

- Posiciones `custodioId null` sin cuenta exchange asociada

### 3.5 Posiciones con mismo activo en varios custodios posibles

- Mismo `activoId` en diferentes brokers/exchange
- Ejemplo: `BTC` en broker `c1` y exchange `c2`

## 4. Propuestas de migración M4 y M5

### 4.1 M4: Reconciliación de pestañas cripto

Para cada pestaña cripto legacy:

| Escenario | Propuesta | Certeza |
|-----------|-----------|---------|
| Pestaña sin posición | `mantener` (legacy) | alto |
| Pestaña + 1 posición | `fusionar` (mover posición al custodio exchange) | alto |
| Pestaña + N posiciones (N>1) | `pendiente` (usuario elige) | medio |
| Pestaña + posiciones de distintos activos | `pendiente` (usuario decide por activo) | medio |
| Pestaña fusionada antes | `aprobada` (ya resuelta) | alto |

### 4.2 M5: Asignación de custodio a posiciones legacy

Para cada posición con `custodioId null`:

| Escenario | Propuesta | Certeza |
|-----------|-----------|---------|
| 1 solo custodio posible (broker/exchange) | `asignar` ese custodio | alto |
| Múltiples custodios posibles | `pendiente` (usuario confirma) | baja |
| Sin custodio posible | `mantener pendiente_asignacion` | medio |
| Ya tiene custodioId | `aprobada` (ya resuelta) | alto |

### 4.4 Estados de propuesta

| Estado | Descripción |
|--------|-------------|
| `pendiente` | Propuesta generada, espera confirmación usuario |
| `aprobada` | Usuario confirmó la acción |
| `rechazada` | Usuario rechazó la acción |
| `pendiente_asignacion` | Sin asignar, espera M5 o decisión manual |

## 5. Flujo de trabajo propuesto

### 5.1 Flujo M4 (reconciliación pestañas)

1. Ejecutar `node scripts/migraciones/m4-pestanas-cripto.mjs --dry-run`
2. Revisar `propuesta-m4.json` generado

## 6. Consideraciones importantes

### 6.1 No borrar datos legacy
- Las posiciones `custodioId: null` pasan a `pendiente_asignacion` o mantienen su estado
- Las pestañas `esPatrimonio: false` permanecen como legacy a menos que se fusionen
- El backup previo siempre está disponible para rollback

### 6.2 Idempotencia
- Si `propuesta-m4.json` o `propuesta-m5.json` ya existen y han sido aplicados, los scripts deben detectarlo y saltar
- Los IDs de propuesta incluyen marca de tiempo para evitar re-procesamiento

### 6.3 Coherencia de patrimonio
- Después de M4 y M5, `calcularPatrimonio()` debe devolver totals consistentes
- Posiciones `pendiente_asignacion` no deben contabilizar en el patrimonio hasta M5 completa
- Pestañas fusionadas no deben duplicar el efectivo
