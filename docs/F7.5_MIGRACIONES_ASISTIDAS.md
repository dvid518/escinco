# F7.5_MIGRACIONES_ASISTIDAS.md — Migraciones asistidas M4 y M5

## 1. Introducción

Este documento describe las migraciones asistidas M4 y M5, que requieren intervención
del usuario mediante propuestas JSON. A diferencia de M1–M3 (automáticas), M4 y M5
proporcionan al usuario vista previa y opciones antes de aplicar cambios permanentes.

**Objetivo:** Reconciliar pestañas cripto legacy (M4) y asignar custodio a posiciones
legacy (M5) de forma controlada, verificable y reversible.

**Restricciones:**
- No tocar M6–M8 (preferencias, F7.6).
- No tocar UI general (F7.7–F7.8).
- No tocar reglas Firestore (F7.9).
- No borrar datos legacy hasta confirmar migración.
- No asignar por símbolo si hay más de un custodio posible.
- Los scripts son idempotentes y verificables.

**Lectura de datos:** Los scripts M4 y M5 usan `scripts/migraciones/lector-datos.mjs` que
lee desde Firestore real (requiere UID) o desde un archivo backup (`--backup=path`).
Ejemplo: `node scripts/migraciones/m4-pestanas-cripto.mjs --dry-run --backup=escinco_backup_2026-11-15.dvid`

**UID:** se resuelve en este orden: `--uid=...`, el `uid` guardado en el backup, y el
UID real del usuario como último respaldo. No hay UID de prueba hardcodeado.

Nota importante: Cuando se usa `--backup=path`, los scripts leen del archivo en lugar de
Firestore. Se acepta tanto el `.dvid` exportado por `ExportarServicio` (`{ formato, uid,
cuentas, posiciones, ... }`, con las posiciones identificadas por `activoSimbolo`) como un
array JSON suelto. Una ruta relativa se resuelve contra la raíz del repositorio.

## 3. Migración M4: Reconciliación de pestañas cripto

### 3.1. Qué hace

Detecta cuentas exchange con `esPatrimonio === false` (pestañas cripto legacy) y
las reconcilia con posiciones existentes:

- **Pestaña sin posición**: Mantener como legacy (no migrar)
- **Pestaña + 1 posición única**: Fusionar (mover posición al custodio exchange)
- **Pestaña + N posiciones**: Marcar pendiente (usuario decide)
- **Pestaña fusionada antes**: Ya resuelta, mantener status quo

### 3.2. Archivo de propuesta: `propuesta-m4.json`

Estructura (ver `docs/F7.5_AUDITORIA_M4_M5.md` para detalles completos):

```json
{
  "migracion": "M4",
  "fecha": "2026-11-15T10:00:00Z",
  "total_pestañas": 5,
  "total_propuestas": 5,
  "propuestas": [
    {
      "tipo": "pestaña_sin_posicion",
      "pestaña": { "cuentaId": "c1", "simbolo": "BTC", "esPatrimonio": false },
      "accion_propuesta": "mantener",
      "motivo": "Sin posiciones asociadas",
      "certeza": "alto",
      "estado": "pendiente"
    }
    // ... más propuestas
  ],
  "estado_general": "pendiente_aplicacion",
  "instrucciones": "Revisar cada propuesta. Editar estado a 'aprobada' para aplicar."
}
```

### 3.3. Flujo de trabajo M4

1. `node scripts/migraciones/m4-pestanas-cripto.mjs --dry-run`
   - Genera `propuesta-m4.json` con todas las propuestas en estado `pendiente`
   - Lee datos desde Firestore o backup JSON via lector-datos.mjs

2. Revisar `propuesta-m4.json`:
   - Cambiar `estado: "pendiente"` a `estado: "aprobada"` para las que se quieren aplicar
   - Cambiar `estado: "pendiente"` a `estado: "rechazada"` para las que se desecha

3. `node scripts/migraciones/aplicar-propuesta.mjs propuesta-m4.json`
   - Ejecuta solo las propuestas con `estado: "aprobada"`
   - Genera `propuesta-m4-reporte.json` con el resultado

4. Verificar resultados:
   - `npm test` debería seguir pasando
   - `calcularPatrimonio()` debe devolver totals coherentes

### 3.3. Estados de propuesta M4

| Estado | Significado | Acción |
|--------|-------------|--------|
| `pendiente` | Propuesta generada, espera revisión | No aplicar |
| `aprobada` | Usuario confirmó la acción | Aplicar en `aplicar-propuesta.mjs` |
| `rechazada` | Usuario descartó la acción | Mantener status quo |

### 3.4. Casos especiales M4

| Escenario | Propuesta | Motivo |
|-----------|-----------|--------|
| Pestaña sin posición | `mantener` | Sin posiciones asociadas |
| Pestaña + 1 posición | `fusionar` | Única posición candidata |
| Pestaña + N posiciones (N>1) | `pendiente` | Usuario decide por cada posición |
| Pestaña fusionada antes | `aprobada` | Ya fue resuelta previamente |

## 4. Migración M5: Asignación de custodio a posiciones legacy

### 4.1. Qué hace

Detecta posiciones con `custodioId null` y propone custodio basado en disponibilidad:

- **1 solo custodio posible**: Asignar con alta certeza
- **Múltiples custodios posibles**: Marcar pendiente (usuario decide)
- **Sin custodios posibles**: Mantener `pendiente_asignacion`
- **Ya tiene custodioId**: Idempotente, saltar

Solo cuentan como custodios las cuentas `broker`/`exchange` con `estado` distinto de
`"archivada"`: una cuenta archivada conserva su historial pero ya no puede custodiar
activos, así que no se ofrece como candidata.

### 4.2. Archivo de propuesta: `propuesta-m5.json`

Estructura (ver `docs/F7.5_AUDITORIA_M4_M5.md` para detalles):

```json
{
  "migracion": "M5",
  "fecha": "2026-11-15T10:00:00Z",
  "total_posiciones_sin_custodio": 3,
  "propuestas": [
    {
      "tipo": "posicion_sin_custodio",
      "posicion": { "posicionId": "p1", "activoId": "BTC", "cantidad": 0.5 },
      "custodio_posible": { "id": "cBroker", "nombre": "Broker Principal", "tipo": "broker" },
      "accion_propuesta": "asignar",
      "motivo": "Sólo un custodio posible, certeza alta",
      "certeza": "alto",
      "estado": "pendiente"
    }
    // ... más propuestas
  ],
  "estado_general": "pendiente_aplicacion",
  "instrucciones": "Revisar cada propuesta en propuesta-m5.json. 'aprobar' (asignar custodio) o 'rechazar' (mantener pendiente_asignacion). Ejecutar: node scripts/migraciones/aplicar-propuesta.mjs propuesta-m5.json"
}
```

### 4.3. Flujo de trabajo M5

1. `node scripts/migraciones/m5-custodio-posiciones.mjs --dry-run`
   - Genera `propuesta-m5.json` con todas las propuestas en estado `pendiente`
   - Lee datos reales desde Firestore o backup JSON

2. Revisar `propuesta-m5.json`:
   - Cambiar `estado: "pendiente"` a `estado: "aprobada"` para las que se quieren aplicar
   - Cambiar `estado: "pendiente"` a `estado: "rechazada"` para las que se desecha

3. `node scripts/migraciones/aplicar-propuesta.mjs propuesta-m5.json --backup=escinco_backup.dvid`
   - Ejecuta solo las propuestas con `estado: "aprobada"`
   - Genera `propuesta-m5-reporte.json`
   - No sobrescribe una posición que ya tenga custodio (idempotente)

4. Verificar resultados:
   - Posiciones antes tenían `custodioId: null`, ahora tienen asignado
   - `npm test` verde
   - `calcularPatrimonio()` coherente

### 4.4. Estados de propuesta M5

| Estado | Significado | Acción |
|--------|-------------|--------|
| `pendiente` | Propuesta generada, espera revisión | No aplicar |
| `aprobada` | Usuario confirmó la asignación | Aplicar en `aplicar-propuesta.mjs` |
| `rechazada` | Usuario rechazó la asignación | Mantener `pendiente_asignacion` |

### 4.4. Casos especiales M5

| Escenario | Propuesta | Certeza |
|-----------|-----------|---------|
| 1 solo custodio posible | `asignar` | alta |
| Múltiples custodios posibles | `pendiente` | baja |
| Sin custodios posibles | `mantener` (pendiente_asignacion) | media |
| Custodio archivado | no se cuenta como candidato | — |
| Ya tiene custodioId | Idempotente | — |

## 5. Scripts involucrados

| Script | Descripción |
|--------|-------------|
| `scripts/migraciones/m4-pestanas-cripto.mjs` | Genera `propuesta-m4.json` (dry-run) |
| `scripts/migraciones/m5-custodio-posiciones.mjs` | Genera `propuesta-m5.json` (dry-run) |
| `scripts/migraciones/aplicar-propuesta.mjs` | Aplica propuestas aprobadas, genera reporte |

### 5.1. Flujo de `aplicar-propuesta.mjs`

```
node scripts/migraciones/aplicar-propuesta.mjs propuesta-m5.json [--uid=...] [--backup=...]
```

1. Resolver el UID (`--uid`, luego el del backup, luego el real) y leer el JSON de propuesta.
2. Leer el estado actual de las posiciones con `lector-datos.mjs` (Firestore o backup).
3. Para cada propuesta:
   - `aprobada`: asignar el custodio; si la posición ya tenía uno, no se sobrescribe
   - `pendiente`: saltar (no aplicar)
   - `rechazada`: contar como rechazada
4. Generar reporte JSON con contadores (`aplicadas`, `rechazadas`, `ignoradas`) y
   guardarlo con sufijo `-reporte.json`.

### 5.2. Consideraciones de seguridad

- **Nunca** aplicar propuestas sin antes revisar el JSON
- **Siempre** generar backup antes de cambios críticos
- Los scripts son idempotentes: aplicar dos veces el mismo archivo es seguro
- Los reports generados permiten rollback informado
- Si hay propuestas aprobadas y no se puede cargar el repositorio (ver 5.3), el script
  aborta **antes** de escribir: no deja aplicaciones a medias.

### 5.3. Limitación: escrituras solo desde el navegador

`aplicar-propuesta.mjs` escribe mediante `js/repositories/PosicionRepositorio.js`, que
usa el SDK web de Firestore cargado por `https://`. Node no puede importar URLs `https:`,
así que **aplicar propuestas desde Node falla con un mensaje explícito** y código de
salida 1. La lectura y verificación con `--backup` sí funcionan. Aplicar de verdad
requiere ejecutar la escritura en el navegador (o añadir en el futuro un cliente Node
con SDK Admin). Es deuda conocida de F7.5, no un fallo silencioso.

## 6. Flujo de trabajo completo

### 6.1. Ejemplo completo M4 + M5

```
Fase de preparación:
  $ node scripts/migraciones/m4-pestanas-cripto.mjs --dry-run
  $ node scripts/migraciones/m5-custodio-posiciones.mjs --dry-run

Fase de revisión (día siguiente):
  $ node scripts/migraciones/aplicar-propuesta.mjs propuesta-m4.json    # Revisar y editar primero!
  $ node scripts/migraciones/aplicar-propuesta.mjs propuesta-m5.json

Fase de verificación:
  $ npm test
  # Verificar que patrimonio es coherente
  # Revisar que no hay posiciones sin asignar inesperadas
```

### 6.2. Validación posterior

Después de aplicar M4 y M5:

```bash
# Verificar tests pasan
npm test

# Verificar patrimonio coherente (ejemplo conceptual)
node -e "
  const { calcularPatrimonio } = require('./js/services/PatrimonioServicio')
  const stats = await calcularPatrimonio({})
  console.log('Patrimonio PEN:', stats.patrimonioPEN)
  console.log('Patrimonio USD:', stats.patrimonioUSD)
  console.log('Posiciones total:', stats.inversionesPEN + stats.inversionesUSD)
  console.log('Sin duplicar, sin perder: ' + (stats.patrimonioPEN > 0 && stats.patrimonioUSD > 0))
"
```
